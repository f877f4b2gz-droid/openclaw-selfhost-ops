# openclaw-selfhost-ops

> 让长期运行的自托管 AI Agent 不烂掉：资产不漂移、日志不灌水、告警不作废、经验不重踩。

一套可直接搬走的运维治理脚本 + 规范文档，纯 bash + 系统自带工具（python3 / curl / ss），不引第三方库，每个脚本单独可用；硬件相关检查缺工具时自动跳过。
从一套每天真实运行的多智能体生产环境里提炼，剥离了内部细节，只留可复用的机制。

---

## 先看这些症状，眼熟吗

- 同一份配置写了两遍，改了 A 忘了 B，两周后不知道哪个是对的
- 临时脚本堆了三十个，没人敢删，也不知道哪个还在被调用
- 巡检每天推送四五十条"报错"，看三天就不看了 —— 然后真正的问题从里面漏过去
- 模型悄悄从免费通道切到付费通道，月底看账单才发现
- 上下文一压缩，上一轮在做什么全忘了，同一个坑踩第二遍
- 踩坑结论写在聊天记录里，一周后检索不到，等于没记

这些不是"用得不熟"，而是缺少**治理机制**。本仓库就是那套机制。

---

## 四层治理，对应上面六条症状

### 一、资产不再漂移

- **唯一真相源**：每条事实只写一处，其他位置只放指针，不复制正文
- **字典式索引**：跨类检索走检字表，不靠记忆
- **草稿存活期考核**：`scratch-sweep.sh` 对"存活 ≥30 天 ∧ 被引 =0 ∧ 连续两轮 =0"的草稿移入回收站，只出清单不动手删
- **被引次数静态分析**：`ref-count.sh` 分层列出共享/被引/依赖/未沉淀/豁免，给"能不能删"提供依据而不是感觉

### 二、日志不再灌水（本版核心）

巡检最容易失效的方式，是把日志里的 error 行全数上报。同源报错一天几十条，三轮之后人就免疫了。

这里改成**按指纹上报**：

| 阶段 | 脚本 | 做什么 |
|---|---|---|
| 归一化 | `log-fingerprint.sh` | 抹平时间/PID/路径/数字/引号内容，脱敏 token/JWT/长串，同类错误归成一个十位短哈希 |
| 记结论 | `log-error-kb.sh` | 每个指纹只登记一次：无害 / 待人工 / 新，附原因、影响、处置、180 天复核期 |
| 只报三个数 | `inspect-daily.sh` | 报告里只有「新 N / 待人工 N / 已忽略 N」+ 最多 3 条新样本 |

实测：同一台机器，按条数是 53 条噪声；按指纹分类后降到「新 11 / 已忽略 42」，需要人看的只剩个位数。

还有一个隐坑写在文档里：**巡检不能扫自己**。助手自身日志被当成系统故障上报，会形成自激循环，实测能占到全部待处理项的四成左右。

### 三、告警不再作废

- **冷却必须能落盘**：去重靠"上次发送时间"文件。目录不可写时冷却静默失效，告警按巡检频率重复推送。脚本启动自检，不可写立刻喊出来。
- **阈值按天设，不按顿设**：花费类告警按"一天的量级"给，不然天天响。
- **模型费用守卫**（`model-guard.sh`）：查主模型是否还在免费通道、免费通道是否可达、付费余额是否见底、有没有会话偷偷钉在付费模型上、24 小时实付花费是否超限。任何一项异常才告警。

### 四、经验不再流失

- **经验扫描**：`exp-scan.sh` 离线聚类重复踩坑与可复用模式，写入有界队列（上限 50、30 天过期、超限归档）
- **会话检查点**（`checkpoint.sh`）：切换模型、上下文压缩、会话重置之前，把「已做·在做·待做」落盘；接续时先读文件，不靠回忆

## 60 秒上手

```bash
git clone https://github.com/f877f4b2gz-droid/openclaw-selfhost-ops.git && cd openclaw-selfhost-ops

# 1. 配置（唯一需要改的文件，且不入库）
sudo install -Dm644 templates/ops.conf.example /etc/openclaw-ops/ops.conf
sudo editor /etc/openclaw-ops/ops.conf

# 2. 全部脚本都支持只读试跑，先看不动手
./scripts/inspect-daily.sh --dry
./scripts/model-guard.sh --dry-run
./scripts/scratch-sweep.sh --dry-run
./scripts/ref-count.sh --list-zero
./scripts/exp-scan.sh --dry-run

# 3. 满意了再接定时任务
crontab -e   # 示例见 cron/ops.cron.example
```

自测（不碰真实环境，临时目录里跑）：`bash tests/smoke.sh`。

无 root 场景：`OPS_CONF=/path/to/ops.conf ./scripts/...`。
依赖缺失不中断：私有辅助库（推送通道等）没配时，脚本降级到本地日志并打印警告，主流程照跑。

## 两条环境级坑（不在脚本里，写在这儿）

机制之外，有些坑是运行环境本身给的。两条都直接影响本仓库的两条主线：日志不灌水、告警不作废。

### 一、跨子卷软链会让文件句柄失效

把 `/volA/xxx` 软链到 `/volB/yyy` 看着省事，但依赖 `name_to_handle_at` / `open_by_handle_at` 的访问统计类服务，跨子卷拿不到句柄，会持续报 `bad file number`（EBADF）。症状很迷惑：文件明明读得到，服务就是不停报错，重启服务也立刻复现。

这类报错会被巡检当成「新错误」反复上报，最后污染整个报错知识库。改用 `mount --bind`，路径不变、对应用透明、句柄正常；写进开机配置时带 `nofail`，挂不上也不影响启动。

**排查要点**：先确认是不是真坏。`find <dir> -xtype l` 数一遍失效软链，是 0 就别再怀疑数据，问题在机制上。

### 二、fuse 挂载断了，进程却还活着

云存储类服务用 rclone/fuse 挂载时，后端掉线后挂载点会留在 `Transport endpoint is not connected` 状态，`ls` 直接报错，但服务进程状态显示正常——巡检看 `systemctl is-active` 会判定健康，属典型的假活。

顺序固定：先 `umount -l` 懒卸载（普通 `umount` 会报 Invalid argument），再 `fusermount -uz`，然后重启挂载服务，挂载点自动重建。**不要先删数据**——文件大概率都还在，只是通道断了。

## 适合 / 不适合

**适合**：长期跑自托管 AI agent、多机协作、资产与日志已经失控的环境。
**不适合**：只想装个聊天机器人、不打算长期维护的场景 —— 这里的机制是按"跑一年不出事"设计的，短期用会觉得重。
