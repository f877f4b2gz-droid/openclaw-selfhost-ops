# OpenClaw 自托管运维治理

> 给"长期自托管的 AI 助手"（OpenClaw 一类）加一套**资产治理**：让文档、配置、备份、技能、记忆、日志**各归其位、有记录、能自检**——省心、可回滚、不烧磁盘、不烧上下文。

## 为什么是"整合"，而不是又一个单点工具

一个人长期跑一个常驻 AI 助手，最难的不是功能，是**运维秩序**。而单环节方案已经很多——备份、记忆、技能、成本各自都有现成项目——**却没人把它们整合成一套**。

本项目就是那套整合：**5+1 类资产的统一治理**（全生命周期 + 每周自动对账 + 台账可回滚）。它**不跟单点工具比"我的备份比你强"**，只做一件事——让分散的规矩**归位、互联、能自检**。

---

## 一、原本的问题（优化前）

长期运行后几乎必然出现的"慢性病"：

| 痛点 | 后果 |
|---|---|
| 文档散落各处、无索引、无状态标记，新稿覆盖旧稿 | 不知道哪份是准的，等于没有文档 |
| 配置改了没备份、没记录 | 出问题无法回滚，只能重来 |
| 日志无限增长（如 cache-trace 单文件涨到 400MB+；服务日志无上限） | 悄悄吃满磁盘 |
| 备份混放、命名随意、无保留策略 | 该有的没有，该删的堆积 |
| 技能无版本；记忆（MEMORY）越堆越厚 | 变更不可追溯；膨胀的上下文每次都在烧 token |
| 会话残留（`*.trajectory.jsonl` / `*.bak-*` / `*.checkpoint.*`）堆积 | 占盘、拖慢 |

## 二、做了什么（优化后）

把资产分成 **5+1 类**，另设「回收站」「自检」两个附件。每类都定：**唯一位置 · 命名规则 · 保留/归档策略 · 变更记录**。

1. **文档** → `docs/` 单一真相源：统一状态头（标题/更新日期/状态）、索引、旧版进 `archive/`。
2. **备份** → 脚本产物与手工备份**分归口**；命名 `名字.bak.YYYYMMDD-HHMMSS`；保留份数硬上限；操作记 `台账.md`。
3. **配置** → 改前先 `.bak`；每日 **core 全量快照**（保 30 份）；常驻 `.last-good`。
4. **技能** → 强制 `VERSION` + `CHANGELOG.md`；清单登记；停用进 `_disabled/`（不删）。
5. **记忆** → `MEMORY.md` 只放**指针/红线**，不堆正文；日记保留 30 天后归档。
6. **日志** → `cache-trace` 超 300MB 原地重写只留最近 **20%**；服务日志超 50MB 截断；轮转件按 7/14/30 天清。
- **附 · 回收站** → `trash/` 保留 30 天，**能 trash 不 rm**。
- **附 · 自检** → 每周 `asset-audit`：逐项体检 5+1 类，**漏登记/超限就告警**（推送 IM）。

## 三、效果（可量化）

- **cache-trace.jsonl**：无上限 → **稳态 170–300MB**（超阈自动瘦身）。
- **core 快照**：无 → **每日 1 份，保留 30 份**。
- **配置回滚**：从"没有"到"**一条 cp 命令**"。
- **文档**：从散乱 → 有索引 + **每周自动对账**（未登记立即告警）。
- **上下文/Token**：只注入**固定小文件**；高频变动文件（日志、状态）全部外置，不进上下文（规则见 `docs/规范-上下文与缓存.md`）。
- **磁盘**：日志、会话残留、旧备份有确定的上限与清理周期。

> 本节及各规范里的具体数字均为 **示例默认（来自实战）**——是长期运行实际调出来的值，非理论建议；可按各文档"四、怎么改"调整。

## 四、状态分级（必须 / 建议 / 可选）

每份规范头部都标一个状态，含义：

- **必须执行** —— 不做会出事（备份、配置、脱敏、日志）。
- **建议执行** —— 不做会积累问题，时间一长发烂（文档、技能、巡检、上下文与缓存）。
- **可选** —— 看情况，按需取舍（记忆归档细节等）。

> 提醒：标"可选"的没人做，规矩就死了。所以只有真正依赖个人偏好的才降级。

## 七、快速上手（5 步）

1. **准备配置**：`sudo install -Dm644 scripts/ops.conf.example /etc/openclaw-ops/ops.conf`，再按本机改路径与阈值（脚本默认读这里）。**无 root** 时放进任意目录，用 `OPS_CONF=/路径/ops.conf` 指定即可。
2. **跑一次体检**：`chmod +x scripts/*.sh`，执行 `./scripts/asset-audit.sh`，看输出（报告写在 `$WORKSPACE/logs/asset-audit.log`）。
3. **挂定时**：参照 `cron/ops.cron.example`，把三条任务放进 `<定时表>`（OpenClaw 用户通常是 `/etc/cron.d/`）。
4. **配告警**：把 `ALERT_CMD` 指到你的推送脚本（IM / 邮件 / Webhook 均可）；留空则只写日志、不推送。
5. **（可选）确认告警推送正常**：`ALERT_CMD` 配好后跑一次 `asset-audit.sh`，能收到测试推送即可；不配也能用，异常只写日志。

> 贡献者额外一步：提交前按 `docs/规范-脱敏.md` 自查——真实路径 / 域名 / 凭据一律不要提交。

## 八、谁适合用

- 自托管 OpenClaw / Claude-Code 一类**常驻助手**的个人用户；
- 跑 NAS / 小主机的玩家（资源有限，更怕日志撑爆）；
- **已经在用零散备份/记忆工具、但它们各管一摊互不相通的人**——想做"合起来一套"的，就是本项目；
- 想要"可回滚、可追溯、少维护"的人。

## 九、常见问题（FAQ）

**Q：我没有 root 权限，能跑吗？**
能。脚本默认读 `/etc/openclaw-ops/ops.conf`，没 root 就用 `OPS_CONF=/你的路径/ops.conf` 指定；告警也可以不配（`ALERT_CMD` 留空）。

**Q：我只想要备份 / 只想要日志轮转，能用吗？**
能，三个脚本彼此独立，挑着用即可。不过本项目价值在**整合 + 自检**，单点分工见 README 开头。

**Q：会不会误删我的文件？**
破坏性脚本支持 `--dry-run`：先跑一遍只报告"会动哪些文件"，确认无误再去掉参数真跑；删除一律先进 `trash/`，且改前先 `.bak`。

**Q：我的目录 / 服务跟示例不一样？**
全部参数化。路径、阈值、日志清单都在 `ops.conf` 里改；文档里一律用占位符（`<工作区>` 等）。

**Q：它和那些单点工具（备份 / 记忆 / 成本）是什么关系？**
不替代，可并用。本项目不追求"某一点更强"，而是把各类资产**归口、对账、可回滚**地管起来。

**Q：会不会很耗资源？**
轻量。体检只做 `stat` / 计数；轮转、备份走 cron，一次几秒到几十秒。

**Q：Windows / macOS 能用吗？**
当前脚本面向 Linux（NAS / 小主机），依赖 `bash`、`cron`、`find`、`tar`；思路通用，移植请自测。

**Q：改坏了怎么回滚？**
每步改动前都先 `.bak`，并在台账里记**恢复命令**；配置类一条 `cp` 就能回去。
