# 规范 · 配置

> 归属：5+1 类资产之"配置"
> 状态：必须执行
> 目的：配置是系统的"接线图"，改错一处可能整站瘫；必须改前有备、改后有记、随时可回。

## 一、为什么要有这条

配置（主程序配置、定时任务、运维脚本）决定系统怎么跑。它有两个特点：**改动频繁**、**影响面大**——一次手滑可能让整个入口挂掉，连带一堆服务不可用。

所以铁律是：**改前先备份，改后先验证，不行就回滚**；并且每次改动都要留痕，能说清"谁、何时、为什么改、怎么退回"。

## 二、规范内容

| 维度 | 规则 |
|---|---|
| 位置 | 主配置 `<主配置>`（OpenClaw 用户通常是 `~/.openclaw/openclaw.json`）；定时任务 `<定时表>`；脚本 `<脚本目录>` |
| 改前 | 先 `cp` 一份 `.bak.YYYYMMDD-HHMMSS` |
| 保留 | 同文件保留最近若干份（如主配置 ~10 份）+ 常驻一份 `.last-good` |
| 快照 | 每日定时**全量快照**（保 N 份），兜底"改坏了、单份备份也坏了" |
| 记录 | 每次改动写台账：时间 / 文件 / 原因 / 恢复命令 |
| 归档 | 过期 `.bak` 转 `trash/` |
| 红线 | 不用高权直改属主文件（除非明确必要）；改任何脚本前先 `.bak`；**禁止把密钥写进配置明文** |

> 上表数值为 **示例默认（来自实战）**，是长期运行调出来的实际值，非理论建议；照抄可用，也可按第四节调整。

## 三、怎么落地

1. 固定一套"改配置"动作：**备份 → 改 → 语法检查 → 生效 → 验证**。
2. 主配置保留最近 10 份，并维护一个 `.last-good`（确认可用后覆盖）。
3. 加一个每日全量快照任务（含脚本、定时表、主配置）。
4. 每次改完在台账写一行，**带恢复命令**。
5. 语法先检查再生效（如 `bash -n`、JSON 校验），别让坏配置直接上线。

## 四、怎么改（按你的情况）

- **个人单机** → 保留 10 份足够，重点保 `.last-good`。
- **关键服务（入口/网关）** → 改前额外"手工备份 + 记录当前可用版本"，改后**立即验证**，失败马上回滚。
- **频繁调参** → 用配置片段/环境变量，别直接改主文件。
- **多环境** → 配置模板化，敏感值走环境变量或密钥文件（见《规范 · 脱敏》）。
- **磁盘紧张** → 份数减少，但 `.last-good` 和每日快照**不能砍**。

## 五、检查（巡检项）

- [ ] 主配置备份数量未超上限
- [ ] `.last-good` 存在
- [ ] 每日全量快照在正常产生
- [ ] 关键脚本有对应 `.bak`
- [ ] 配置里**没有明文密钥**（抽查）
- [ ] 过期 `.bak` 已转 `trash/`，未就地堆积
