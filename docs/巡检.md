# 规范 · 巡检

> 归属：跨类体检（横跨 5+1 类）
> 状态：建议执行
> 目的：规范写了不等于执行了；用**定期自动体检**把"没做到"揪出来并主动提醒。

## 一、为什么要有这条

规矩定了没人查，等于没定。人会忘、脚本会漏、升级会冲掉改动——偏差就是这么悄悄累积的。

巡检的价值是**自动发现偏差**：文档漏登记、配置没备份、日志超限、技能缺版本、记忆没归档……不用靠人记，机器每周扫一遍，有问题**主动提醒**，没问题保持安静。

## 二、规范内容

| 巡检对象 | 检查什么 | 异常动作 |
|---|---|---|
| 文档 | 标题 / 状态头是否存在、是否登记进索引 | 未登记即告警 |
| **自建脚本** | `scripts/` 下的脚本**是否逐个登记进台账**（一行一个才能被搜到） | 漏登记即告警 |
| 备份 | 手工备份体积、核心快照份数、台账是否还在更新 | 超限 / 停滞即告警 |
| 配置 | 备份份数、`.last-good`、清理任务**是否有日志重定向** | 缺失即告警 |
| 技能 | 自建技能 VERSION / CHANGELOG、清单一致性 | 缺失即告警 |
| 记忆 | 超期日记、长期记忆是否堆正文 | 超期即告警 |
| 日志 | 缓存追踪不超上限、无 >1GB 日志、轮转件在清理 | 超标即告警 |
| **项目区** | 固定五文件是否齐、`STATUS.md` 是否超期、是否登记索引、协议是否错位到 `design/` | 缺失 / 超期即告警 |
| **自备份** | 第二存储是否挂载、daily 快照是否超 2 天未更新、云落点是否可达 | 中断即告警 |
| 脱敏 | 忽略规则、待推文件密钥扫描 | 命中即告警 |
| 回收站 | `trash/` 是否有超 30 天未清 | 超期即清理 |
| 频率 | 每周一次（可配），结果写入巡检日志 | — |
| 通知 | 发现异常时**推送**（IM / 邮件），正常则静默 | — |

> 上表数值为 **示例默认（来自实战）**，是长期运行调出来的实际值，非理论建议；照抄可用，也可按第四节调整。

### 关于"清理任务必须有日志"

这条判据值得单独说：清理类脚本一旦静默失败（比如路径写错、权限不足），
磁盘会继续涨而**没有任何人知道**。所以巡检会把"清理任务有没有日志重定向"当成异常项报出来——
**没日志的清理，等于没跑**。同理，检查 `log-rotate` 的日志文件是否存在，就是在确认"轮转真的在跑"。

## 三、怎么落地

1. 用 `scripts/asset-audit.sh` 按上表逐项检查，输出写 `$WORKSPACE/logs/asset-audit.log`。
   ```bash
   OPS_CONF=/etc/openclaw-ops/ops.conf ./scripts/asset-audit.sh --dry-run   # 先预览
   OPS_CONF=/etc/openclaw-ops/ops.conf ./scripts/asset-audit.sh             # 真跑（写日志）
   ```
2. 只在**发现异常**时推送，正常保持静默（避免打扰）。推送命令配在 `ALERT_CMD`。
3. 用定时任务每周跑；**以 root 运行时才推送**（权限足够才准）。
4. 巡检日志本身也要有上限（超 1MB 截断保留最近 1000 行）——脚本已内置。
5. 把"漏登记 / 漏备份"这类**软偏差**也纳入——它们最容易悄悄累积。
6. 可选范围都可通过 `ops.conf` 关掉（`SCRIPTS_LEDGER_DOC` / `DOCS_LEDGER` / `PROJECTS_DIR` /
   `SELF_BACKUP_ROOT` / `CLOUD_DEST` 留空即跳过对应小节），不必为用不上的项改脚本。

## 四、怎么改（按你的情况）

- **机器多** → 每台各跑，汇总一份总报告。
- **只在出事时才想知道** → 可降频为"仅在异常时运行"。
- **要历史趋势** → 巡检日志按月归档，别只留最新。
- **不想被打扰** → 只推"必须处理"的项，其余进日志。
- **资源紧张** → 巡检做轻量检查（只 stat / 计数，不深扫）。
- **不用项目区 / 没有第二存储** → 把对应配置留空，对应小节自动跳过并如实打印"（未配置，跳过）"，不会误报。

## 五、检查（巡检项）

- [ ] 巡检任务在按时运行（看日志时间戳）
- [ ] 巡检日志本身未超限
- [ ] 告警通道有效（发一条测试能收到）
- [ ] 上次巡检的所有告警是否已处理
- [ ] 巡检覆盖了全部 5+1 类 + 脱敏 + 回收站
- [ ] 软偏差（漏登记 / 漏备份）已被纳入检查

## 六、报错治理：按指纹，不按条数

巡检最容易失效的方式是「把日志里的 error 行全数上报」。一天几十条同源报错会把真正的问题淹掉，几轮之后人就不看了。

做法是三层：

1. **归一化**（`scripts/log-fingerprint.sh`）
   时间、PID、路径、数字、十六进制、引号内容全部抹平，token / JWT / 长 blob 一律脱敏。
   同一类错误无论出现多少次，得到同一个十位短哈希。

2. **记结论**（`scripts/log-error-kb.sh`）
   每个指纹只登记一次结论，三选一：
   - `known-harmless`：已知无害，不再上报
   - `known-manual`：需要人判断，进待人工清单
   - `new`：没见过，进待研究清单
   登记时附原因、影响、处置动作、复核日期，180 天后自动到期重审。

3. **只报三数**（`scripts/inspect-daily.sh`）
   报告里只出现「新 N / 待人工 N / 已忽略 N」，外加最多 3 条新报错样本。

实测效果：同一个系统，按条数报是五十多条噪声；按指纹分类后，需要人看的通常只剩个位数。

### 别把巡检自己的日志扫进去

如果运维助手本身写日志，而巡检又扫 `/var/log` 全目录，就会形成自激：
助手的心跳、重试、告警记录被当成「系统报错」上报，下一轮又产生新的告警记录。
实测这类噪声能占到全部待处理项的四成左右。

规则：巡检只扫系统日志和各应用的 `error.log`；助手自身日志必须显式配置 `INSPECT_SELF_LOGS` 才会被扫。

## 七、告警降噪的两个硬要求

1. **冷却状态必须可落盘**
   去重靠「上次发送时间」文件。目录不存在或不可写时，冷却静默失效，告警会按巡检频率重复推送。
   脚本启动时应自检该目录，不可写要立刻提示，而不是继续跑。

2. **阈值要能调，且默认别太敏感**
   阈值过低等于没有阈值。花费类告警建议按「一天的量级」设，而不是按「一顿饭的量级」设。
