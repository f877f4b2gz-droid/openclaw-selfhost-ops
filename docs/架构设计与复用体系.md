# 架构设计与复用体系

更新日期：2026-10-16　状态：设计文档（D1–D5 部分条款已落地，见 §七）
用途：将「以单一总纲索引全部资产/项目/脚本 + 高频复用上提」的设计初衷整理为可讨论、可落地的方案。
相关：《信息资产管理规范》（字典体例·总纲）、《项目区规范》、《脚本体系治理》、《规则库》、《踩坑总表》、《经验库》

---

## 一、设计初衷（三条核心诉求）

1. **要一个总纲**：文档/脚本/项目/杂项规模增长后，需要顶层记录「做过哪些项目、用过哪些能力」。
2. **总纲要覆盖"所有操作容器/能力"，不只最近项目**：从总纲定位某个能力（如"要调用 X"）→ 进入下一级 → 选中条目 → 查看「用它做过什么 / 通过什么方式成功过 / 复用哪些脚本与命令 / 踩过哪些坑（避免重犯）」。**成功经验持久化**。
3. **高频复用要上提到上一层**：以统一通知出口为参照——所有推送走同一入口，避免各自重复造轮子。常用代码/脚本需**目录归纳 + 注释**，调用即取。并权衡：**调用 vs 重写**。

> 注：以下方案不照搬原始步骤，取其大意；本阶段只做归纳，后续经讨论与论证逐步推进。

## 二、三层结构（目标 → 现状映射）

| 层级 | 目标 | 现状对应 | 状态 |
|---|---|---|---|
| 一级·总纲 | 记录做过什么、用过什么 | `wk-find` 跨类检字表（21 类） | 已有 |
| 二级·条目 | 用它干过啥 / 怎么成功的 / 复用命令 / 踩过的坑 | 各类台账"字头+一句话"；经验/坑分散在别处 | **半成** |
| 三级·文件 | 具体文件 | 各台账/文档本身 | 已有 |

## 三、现状盘点（已有能力，约八成落地）

- **一级总纲**：`wk-find`（总目 21 类：文档/项目/规则/技能/脚本/子域名/快捷指令/固件/踩坑/经验/清理/通道/选型/待办/通知/音乐/知识库/定时/任务…）。设计铁律：只读权威源、不建索引副本 → 零漂移。
- **各类权威源**：文档 `docs/README.md` │ 项目 `projects/README.md` │ 规则《规则库》 │ 技能《技能与插件清单》 │ 脚本《系统资产台账》 │ 固件《固件台账》 │ 子域名《子域名台账》 │ 快捷指令《快捷指令清单》 │ 坑《踩坑总表》 │ 经验《经验库》。
- **复用层（已存在）**：① 函数库 `/usr/local/lib/wk.sh`（`wk_notify`/`wk_log`/`wk_bin`/`wk_fail_inc`/`wk_lock`）；② 单一入口脚本 `qq-send.sh`（统一推送）、`lan-query.sh`（统一取数）。
- **治理规则（已存在）**：《信息资产管理规范》（字典体例 + 五必备项 + **检索键**）、AGENTS「接口约定」、《脚本体系治理》。

## 四、缺口

- **G1** 二级条目只"字头+一句话"，**未把"经验/复用命令/坑"绑定到条目**——单一关键词带不出全部关联信息。
- **G2** 容器（Docker）未纳入检字表。
- **G3** 复用层未显式成类，**"上提门槛"未写进规则**，谁复用谁去重无约定。
- **G4** 「每个资产：能干什么 / 成功过什么」缺少统一字段与聚合。

## 五、备选方案（待裁决）

- **D1 二级条目如何聚合经验/坑？**
  - 方案 A（轻量）：给《经验库》/《踩坑总表》每条打 `@检索词@`，`wk-find <词>` 一次带出「资产 + 复用命令 + 经验 + 坑」。**不新建副本，零漂移**。
  - 方案 B（重量）：每个重要条目建独立"条目页"（项目已采用此模式，但资产类数量大，维护成本高）。
  - 倾向：A 为主，仅对"大项目"使用 B（`projects/` 已在做）。
- **D2 复用"上提门槛"定多少？** 倾向：同一逻辑重复 ≥3 处，或属"出口型/取数型"能力 → 上提为共享函数/单一入口；上提必须带**注释 + 检索词 + 台账登记**；"没注释/没检索词/没登记 = 查不到 = 没复用"。
- **D3 调用 vs 重写？** 倾向：**调用优先**；动手前先 `wk-find`；仅当场景特殊、复用会引入耦合/副作用（如 `radarr-relay.py` 约定"独立勿动"）才局部自写并注明原因。
- **D4 容器类**：并入 `wk-find`（数据源《Docker容器与存储》）。
- **D5 是否为台账增设"用途/成功案例"必填字段**：加字段即加维护成本，需权衡。

## 六、实施步骤（裁决后执行）

1. 确定 D1–D5 的方案与取舍。
2. 落规则：将"复用判据 + 上提门槛"写入《规则库》。
3. 落索引：`wk-find` 增设「复用」类、补「容器」类。
4. 落标签：为《经验库》/《踩坑总表》打检索词。
5. 每步：备份 → 修改 → 验证 → 记入 `CHANGELOG`/台账。

## 七、已定修正（2026-10-17 补充，P4/P6）

**P4·`scratch/` 兜底（已写入 scratch/README + 规则库）**
1. 存活期 **30 天**：新进文件**从进入 `scratch/` 之日起算**（不以文件 mtime 为准）。
2. **存量文件豁免**：规则上线前已在 `scratch/` 的文件**不自动清理**，仅输出清单人工复核。
3. 被引 ≥1 次 → 续期；=0 → 到期候选；**连续两轮（约两个月）=0 才清理**。
4. 30 天起算点 = **机制上线日**；**首次扫描只出清单、不删除**；存量先豁免，积累引用记录后再启动考核。

**P6·被引次数（只做脚本层，分层考核）**
- 静态扫描（grep 引用）→ 输出并入 `wk-find`，增加「被引次数」字段。
- 扫描范围**只限未提纯层**（`scratch/`、临时脚本区、散落脚本）。
- **豁免层**：`tools/`、`/usr/local/bin`、`wk.sh`、`qq-send.sh` 及所有已登记为砖/墙层的资产，不参与「=0 即清」。
- 判据分层：未提纯层 =0 且 30 天未动 → 清理；砖层永不自动清理、仅展示引用次数；墙/房层不考核。

**P11·D1–D5 落地口径**
- D1 检索词：每条约 3–5 个。
- D2 上提门槛：≥3 处 / 出口取数型 / 易错涉权限。
- D3 调用 vs 重写：成本对比 —— **读接口+调用比重写更贵时才重写**。
- D4 容器并入检字表（见 P10）。
- D5 高频台账增设「用途/成功案例」字段（通知、容器、复用脚本三类）。
